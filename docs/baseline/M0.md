### 搭建要点（国内网络 + VMware 特有的坑）

- **ROS apt 源换成清华镜像**：`packages.ros.org` 实测只有 9 KB/s。把 `/etc/apt/sources.list.d/ros2.sources` 的 URI 改成 `https://mirrors.tuna.tsinghua.edu.cn/ros2/ubuntu`，并把 `Types: deb deb-src` 改为 `Types: deb`（镜像没有源码包）。
- **rosdep 换成清华镜像**：`rosdep init` 访问不了 GitHub raw。手写 `/etc/ros/rosdep/sources.list.d/20-default.list` 指向 `https://mirrors.tuna.tsinghua.edu.cn/github-raw/ros/rosdistro/master/...`，并 `export ROSDISTRO_INDEX_URL=https://mirrors.tuna.tsinghua.edu.cn/rosdistro/index-v4.yaml`。
- **Gazebo 传感器渲染**：VMware 虚拟 GPU 没开 3D，不提供 OpenGL 3.3，导致激光雷达不出数据。在 `~/.bashrc` 里强制使用 Mesa 软件渲染：
  `export LIBGL_ALWAYS_SOFTWARE=1 MESA_LOADER_DRIVER_OVERRIDE=kms_swrast GALLIUM_DRIVER=llvmpipe MESA_GL_VERSION_OVERRIDE=4.5`
  另外把 `ubuntu` 加进了 `render`、`video` 组。
- **验收脚本依赖** `ripgrep`（`rg`），需要另外 `apt install ripgrep`。
- 编译：`MAKEFLAGS=-j2 colcon build --symlink-install --parallel-workers 2 --cmake-args -DCMAKE_BUILD_TYPE=Release`，19 个包，耗时 6 分 22 秒。

## 一键演示：完整跑通（headless）

```bash
ros2 launch robot_bringup amr_demo.launch.py gui:=false use_rviz:=false
```

服务就绪后约 4 分钟内，演示编排器 `amr_sim_demo_director_node` 依次完成：检查顶升模块 → 站点确认 → 预约收货门 → 申请电梯 → 重定位 → 封路、限速 → 对桩充电（`CHARGING`）、出桩 → **站点运输**（取货站 `WAIT_LOAD`，确认上货 → 卸货站 `WAIT_UNLOAD`，确认卸货 → `FINISHED`）→ 解封 → **双车路权**（alpha 先占路，beta 申请被拒；alpha 释放后 beta 才拿到路权）→ 机会充电 → 模拟障碍上报与清除 → 解除限速。

- 编排器自己会发装卸确认，所以站点运输能走完。说明门控逻辑本身正常，上面 A 类失败是验收脚本没跟上。
- "beta 申请被拒 → 等 alpha 释放 → 再申请"就是现在"整条路径一次锁完、拿不到就失败、没有等待队列"的行为，也正是模块二要改的地方。
- 带图形界面（`gui:=true use_rviz:=true`）要在虚拟机桌面里运行，这次没有验证。

## 补充（2026-11-15 晚）：修好装卸确认后重跑 A 类 20 个用例

**改动**：验收脚本层面，不碰业务代码。

- `scripts/robot_wait.sh` 新增后台"自动装卸确认器"（`start_station_auto_confirm` / `station_auto_confirm_loop`）：轮询 `/mission_runner/state`，看到 `WAIT_LOAD` / `WAIT_UNLOAD` 就按消息里的站点名调用 `/v2/confirm_load` / `/v2/confirm_unload`，和演示编排器做的事一样。
- A 类 20 个脚本里的 19 个（`picking_wave` 不走站点运输，没改）在提交工单前启动确认器。
- 加了门控后单个站点运输从约 25 秒变成约 50 秒（取货段 → 确认 → 卸货段 → 确认），脚本里的等待上限从 25/35/45 秒统一抬到 90 秒；一个期限里等多个任务的 `scenario_workflows`、`station_sequence` 抬到 180 秒。

**结果**：20 个里 14 个转为通过，总计 **73 / 99**（原 59）。`safety:route_locks` 已能测路权，M1 的安全网齐了。[`m0_acceptance.tsv`](m0_acceptance.tsv) 里这 20 行已更新并标注。

剩下 6 个失败，原因和装卸确认无关，M0 基线日志里是同样的报错，重新归类：

**E. 入队即锁整条路径，链式工单第 2 步被拒（5 个）**
`mission:station_order_batch`、`mission:workflow_pause_resume`、`business:scenario_workflows`、`business:industry_workflows`、`business:more_industry_workflows`
提交响应：`scenario workflow rejected at step 2: ... station transport route lock rejected: route resource locked: route_node:storage_a by ..._step_1`。第 1 步（receiving → storage_a）在入队时就锁住了整条路径含 `storage_a` 路口，第 2 步（storage_a → packing）申请时被拒，工作流整体拒绝、只排进第 1 步。这就是现有"整条路径一次锁完、没有等待队列"的直接后果，属于 M2（滚动申请 + 等待队列）要改的行为；这 5 个用例可以作为 M2 的验收信号，M1 不用管。

**F. 脚本和现行业务逻辑不一致（1 个）**
`business:picking_wave`：脚本先 `confirm_pick`（拣 8/10，节点直接进 `SHORT_PICK`），再调 `report_short_pick`，被拒 `fulfillment short pick is not pending: state=SHORT_PICK`。上游后来把短拣判定并进了 `confirm_pick`，脚本没跟着改。改脚本或改逻辑都行，待定。
