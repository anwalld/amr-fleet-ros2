# M1：把路权拆成 TrafficService

记录日期：2026-11-16。起点：M0 基线提交 `7f8cdac`（见 [`M0.md`](M0.md)）。
目标（二开计划第 6.2、7 节）：把 `mission_runner_node.cpp` 里的路权状态和服务搬进一个 `TrafficService` 类，只移动代码、不改逻辑，对外服务名和类型不变；原有交通相关验收脚本全部通过；节点文件行数下降。

## 做法

按二开计划 6.2 节的约定：

- `TrafficService` 是普通 C++ 类，构造时拿到节点指针和共享上下文 `MissionContext`，在构造函数里注册自己的服务。
- 被多个组件读写的状态放进 `MissionContext`（新文件 `robot_tasks/mission_context.hpp`）：路权表 `route_locks`、按任务索引的 `route_locks_by_mission`、站点文件路径 `station_file`、`traffic_intersection_locks_enabled` 开关。节点里原来的同名成员改成 `context_.xxx`，调用处不变。
- 决策逻辑仍是 `traffic_reservation.cpp` 里的 `Plan*` 纯函数，没动；`TrafficService` 只做"取状态 → 调纯函数 → 写回状态 → 填响应"。
- 保持单线程执行器，不加新锁。
- `TrafficService` 只编进 `mission_runner_node` 可执行文件（`add_executable` 多一个源文件），`robot_tasks_mission_profile` 库不依赖 rclcpp 的状况不变。

一次提交只搬一块，三个提交：

| 提交 | 搬的内容 | 节点文件行数变化 |
| --- | --- | --- |
| `7961935` | 四个共享状态搬进 `MissionContext`；`SanitizeId` 从节点匿名命名空间搬到 `robot_tasks/sanitize_id.hpp` 供组件复用 | 6224 → 6210 |
| `723d02a` | 新建 `TrafficService`，搬入 `BuildRouteLockIds` / `ReserveRouteLocksForMission` / `ReleaseRouteLocksForMission` 三个包装函数，节点改调 `traffic_service_->` | 6210 → 6198 |
| `ca6be34` | 五个服务 `/v2/block_station_route`、`/v2/unblock_station_route`、`/v2/list_traffic_reservations`、`/v2/clear_traffic_reservation`、`/v2/detect_traffic_deadlock` 的注册与处理函数搬入（`PlanTrafficDeadlockDetection` 的调用随 `DetectTrafficDeadlock` 一起搬）；节点删掉对应服务成员、`RouteLockId` 包装和五个 srv 头文件 | 6198 → 6050 |

几点说明：

- 任务单里列了 4 个服务，`/v2/clear_traffic_reservation` 同样只操作路权表（演示编排器用它释放 alpha 的路权），一并搬了。
- `ReleaseAllResourcesForMission` 留在节点里：它走 `MissionResourceCleanupBehaviorTree`，同时释放设施预约和路权，属于任务生命周期的一部分；只是把它引用的路权表改成 `context_.route_locks`。
- 处理函数原来是 `template <typename RequestT, typename ResponseT>`，实际只有一种实例化，搬过去后写成具体类型，逻辑一字未改。
- 节点里的 `BuildRouteLockIds` 包装函数原本就没有调用方（入队门控直接用 `robot_tasks::BuildRouteLockIds`），按"只搬不改"原则原样搬进 `TrafficService`，没有删。

### 两个"PASS 变 FAIL"的用例：A/B 对照

为排除拆分引入问题，在同一台虚拟机上把 `robot_tasks` 清掉重编（`rm -rf build/robot_tasks install/robot_tasks`），分别用 M0 提交 `7f8cdac` 和 M1 提交 `ca6be34` 的二进制单独重跑这两个用例，并用 `strings mission_runner_node | grep -c TrafficService` 核验二进制版本（M0 为 0，M1 为 49）：

| 用例 | M0 二进制（5 轮） | M1 二进制（10 轮，含全量那次） |
|---|---|---|
| mission:reprioritize | 1 / 5 通过 | 2 / 10 通过 |
| safety:localization_auto_recovery | 2 / 5 通过 | 7 / 10 通过 |

两个用例在 M0 代码上同样不稳定，M1 通过率不低于 M0，判定与拆分无关，是当天虚拟机负载下的偶发。

- `mission:reprioritize` 失败原因：脚本每轮用两次 `ros2 topic echo --once` 轮询 `/mission_runner/state`，两条任务的目标点只相距 0.1 米、很快跑完；虚拟机慢时第一次轮询返回前 `reprio_second` 已完成并切到 `reprio_first`，脚本永远看不到 `seen_second`，30 秒后报 `did not finish; seen_second=false`。失败时耗时 39～56 秒，通过时 15～27 秒。脚本不碰路权接口。
- `safety:localization_auto_recovery` 失败原因：`localization covariance too high: 1.2`（阈值 0.5），定位健康没在时限内恢复到 OK/RECOVERED。脚本不碰路权接口。

> 注意：第一次 A/B 时切回 M0 源码后 `robot_tasks` 编译失败（CMake 缓存仍引用 `traffic_service.cpp`），验收跑的还是 M1 二进制，数据作废；以上数据来自清掉构建目录后的第二次 A/B。做 A/B 必须核验二进制版本。

### 对 M2 的提示

`mission:reprioritize` 的竞态可以通过让脚本订阅一次事件流（`/v2/list_mission_events`）而不是轮询状态来消除；这是脚本问题，不在 M1 范围，M2 做链式工作流脚本时顺手修。
