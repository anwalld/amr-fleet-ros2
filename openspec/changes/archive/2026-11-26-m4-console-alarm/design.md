# Design

## Context

Ops 工作区已实现异步操作和结果关联。正式夜跑留下阶段 3 的复验待办，故障监控脚本修复已专项通过。本变更沿用现有工作区和此次修复，两项一起正式复验。

## /opsx:explore

- 当前车队轻量仿真代理在自身 20 Hz 定时器积分速度。既有单车底盘急停服务位于速度复用器，直接调用该服务无法阻止仿真代理自身积分。选择在轻量仿真明确启用车队控制节点和运动门控，节点接收并保持停止状态，代理保留任务阶段和路权。
- 连接恢复可以销毁并重建 ROS 执行器，也可以利用已有 DDS 发现和读轮询。选择原连接持续轮询，观测快照与路网恢复，保留窗口和地图，避免操作回执交叉或自动重提。
- 部署可独立打包 ROS 安装树，也可复用 colcon 安装前缀并提供 Ubuntu 应用启动器。现有项目依赖 ROS Jazzy 和工作区包，选择后者，并在安装环境验证。

## Decisions

1. 事件与告警读取快照事件、车队事件和 `/fault_supervisor/state`，有界保存界面记录。重复故障状态合并，来源及其原始状态保留。回放仍按现有记录类型展示可用事件。
2. `fleet_sim.launch.py` 启动车队停止节点。服务 `/v2/set_fleet_sim_stop` 接收显式布尔值，状态主题 `/fleet/sim_stop/state` 由仿真节点发布。状态每 0.5 秒刷新，并在变更后即时发布。节点启动时进入停止状态。现有仿真用例按原配置启动，Alarm 用例显式启用车队门控并确认解除初始停止。启用门控的代理在无状态或超过 2 秒未收到状态时停止运动；车队停止不清除任务和路权。解除前界面要求确认，断开期间读数过期。车队控制状态反映控制节点设定，各车实际动作另用里程计观察。
3. 连接状态按成功快照和路网应答确认，保留最后一次可显示数据，重新连接时立即请求路网。保留 Ops 请求关联和超时行为。回放无需新 ROS 接口。
4. Ubuntu 启动器使用已 source 的工作区或在生成位置绑定安装前缀。安装验证包含实时和回放程序。移动安装前缀后重新生成启动入口。
5. 阶段 7 保持原 Ops 数据表和判定，加入 Alarm 独立用例与可追踪证据。第 8 阶段报告和 Dagu 终态复查需读取两者。正式夜跑只启动一次共同快照。

## /opsx:verify 设计核对

告警和恢复对应任务 1，仿真停止链路对应任务 2，安装对应任务 3，合跑和资料对应任务 4。Core 的读服务边界、Ops 写请求的操作触发约束、回放兼容和既有夜跑参考均沿用。
