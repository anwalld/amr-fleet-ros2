# Design

## Context

M4-core 的 RosBridge 在独立 QThread 中运行 ROS 执行器。Qt 核心通过数据源接收快照、地图和交通状态，可在 Mac 上独立运行回放和单测。任务表当前混合执行中任务、排队任务和远程车队任务，工作流服务以订单号为目标。TrafficService 持有当前路权及暂停分组。

## Goals / Non-Goals

- 保持 Qt 核心可独立测试，现有 rosbridge 与回放的读取通路共用。
- 实时模式与服务就绪控制按钮可用性。此版本的部署范围是已有受信 ROS 仿真域；REST 网关的角色策略只覆盖经网关的调用。运维区是界面分区。

## Decisions

### 1. 从独立的操作接口发请求

主窗口接收可选的操作接口，Qt 核心定义普通请求、结果和错误数据。RosBridge 在原有 ROS 线程接入客户端，QtTest 注入替身，回放不提供操作接口。保留当前 MainWindow 的只读构造用法，实时程序显式注入操作接口，回放和既有 QtTest 调用方继续按原方式构造。入口沿用现有窗口和 bridge 的生命周期。Qt 界面将操作投递到线程安全队列，用 ROS 执行器回调取出并调用服务；当前 QThread 运行 spin()，不要依赖其 Qt 事件循环派发槽。结果通过带标识的 Qt 排队信号回到窗口。关闭时停止接收操作、取消执行器、等待线程退出并清理挂起请求。

界面以稳定的订单号、任务号、车辆号或资源号保存目标。刷新表格后按标识恢复有效选择，目标消失则失效。工作流控制通过明确输入或选中已知的订单号进入，使用订单号请求工作流状态。

### 2. 复用现有操作入口

| 操作 | ROS 服务与状态依据 |
| --- | --- |
| 工作流下单 | 打开表单时调用 `/v2/list_scenario_workflows`，以场景号、工作流号和优先级构造 `/v2/submit_order` 的 `scenario_workflow` 请求。界面在提交前持有订单号，受理后显示子任务编号。 |
| 查询和控制工作流 | `/v2/get_workflow_status`、`/v2/pause_workflow`、`/v2/resume_workflow`、`/v2/cancel_workflow`。提交时带订单号和是否包含运行中子任务的设置。回执之后按订单号查询。 |
| 车队站点搬运 | `/v2/submit_fleet_station_task`，提交前持有任务号。受理后记录分配车辆与任务中枢任务编号。远程派发用快照的远程任务字段，本地派发用返回编号在任务中枢的队列、活动任务和近期事件里核对。 |
| 封路和解封 | `/v2/block_station_route`、`/v2/unblock_station_route`。由选中路段取得站点对，封路采集原因，状态由交通消息确认。 |
| 车辆调度资格 | `/v2/update_fleet_robot_state`，只置 `update_enabled`。用快照的启用字段核对。 |

车队搬运使用有类型的服务，它直接返回任务号、车辆号和任务中枢编号。由表单生成请求，避免让操作员填写通用 JSON。工作流控制复用服务器对订单与子任务的归属判断，界面按已知订单号查询。

请求带本地关联标识，异步返回。写请求在 3 秒超时后显示「结果未知」，复用 `RequestTracker` 的单调时钟、request_id 校验和 remove_pending_request 清理机制。超时后通过订单查询或快照核对同一目标；已进入 Qt 队列的旧回执只更新原操作记录。新操作的显示按本地操作标识匹配。等待期禁用同一目标的重复提交。对写请求不自动重试。回执用于解释受理或拒绝，地图和列表仍由实时数据驱动。

### 3. 以服务端预览为清理确认依据

新增 `/v2/preview_traffic_reservation_clear`，以资源号返回占用者、待释放资源和待解除暂停车辆。占用不存在时返回明确状态。这个查询以 TrafficService 内部的路权与暂停分组为依据。客户端快照方案只能看到采样时的占用，且没有完整暂停分组。

新增 `/v2/clear_traffic_reservation_if_matches`，接收资源号、预期占用者和两个确认过的集合，返回成功、冲突或错误。集合按成员比较，排序差异不构成冲突。后端用同一套决策计算预览和提交时的影响，在当前单线程执行器的一次回调内完成校验和修改。占用或集合有变化时直接返回，调用方重新预览并要求重新确认。匹配后复用原有的清理、解除暂停以及补授予路径。

只比较占用者可以挡住换车，但同一车的路权或暂停分组也可能变化。本设计同时比较两个集合，使执行范围和确认内容一致。旧服务保留为兼容入口。

### 4. 表单、查询与兼容入口

工作流下单从目录选择场景和工作流，提交前生成在后端可原样使用的唯一订单号，以 Qt JSON 序列化 scenario_id、workflow_id 和布尔选项。搬运单使用独立的任务号，站点来自已加载的路网。两种表单默认空闲即启动、关闭抢占。取消对话框固定订单号和影响正在执行子任务的选择，关闭确认框不发送请求。任务表每次 reset 前保留类别和稳定标识，刷新后恢复或清空；子任务行不能自行推导工作流订单号。

取消的业务回执包含 canceled_mission_ids 与 active_cancel_requested。后者只表示已请求，运行中子任务的最终结果通过事件核对。`BuildWorkflowStatusSnapshot` 根据当前队列、活动任务和完成事件构造视图，队列清空后查询可能返回 UNKNOWN。界面保留取消回执并按真实查询结果展示。远程任务继续使用现有状态回报链路。

### 5. 已有实现的复用与新增边界

- `robot_console_core/src/resource_id.cpp` 的 parseResource、edgeKey、isBlockOwner 已处理路段、路口及封路标记。操作入口和原地图共用这些标识和既有车队、交通模型。Qt 的注册元类型与 SmokeMetrics 延用 Core 的口径。
- `PlanTrafficReservationClear`、`ReleaseRouteLocksForMission`、`UnfreezePausedGroupOf` 和 GrantWaiters 已承担决定清理类型、释放、解冻与补授予。新增逻辑限于读取影响及比较前置条件。用同一释放计划产生预览和执行结果，覆盖旧任务号、同一车辆多工单及共享路权。预览列出的解冻车辆表示后端清除了兜底暂停标记，车辆实际获路或恢复移动由后续交通和位置观测单独确认。两个服务加入 robot_interfaces_mission 的接口生成；robot_console 的 CMake、包清单和测试目标补足 robot_interfaces_fleet 的直接依赖。
- 预览请求传 resource_id，响应给出 found、owner_id、resource_ids、resume_robot_ids 与 message。条件清理提交上述目标和显式预期值，响应以可机器区分的结果表示成功、冲突或请求错误，同时带 message。资源不存在时预览 found=false，提交旧预览则冲突。服务不可用时禁用相关按钮并提示，禁止退回旧的无条件清理服务。
- 旧调用者继续使用原清理服务。新客户端遇到超时保留未知状态；服务拒绝时显示其原因。清理成功后资源可能已补授给等待者，核对原占用者释放和补授予事件。测试冲突时比较目标相关状态并观察本次调用的副作用，后台定时补授予单独取证。

## Risks / Trade-offs

- 系统繁忙时确认后可能多次发生冲突。对话框保留目标资源，刷新影响并提示重新确认。资源已无占用时禁用提交。
- 清理后等待者可能立即拿到路权。界面呈现后端清理结果和最新占用者，按实际观测显示状态。
- 快照和近期事件只能覆盖已出现的数据。查询超时或证据不足时显示未知，避免依据任务行消失推断操作已完成。

## Migration Plan

Apply 从包含 Core 合并提交的主线对齐。Core 归档后再同步 Ops 的 operator-console 增量。先部署新增路权服务，再启用运维区清占用。旧后端缺少新服务时，该操作入口显示不可用。回退调度台可以恢复 Core 的实时展示与回放。

## 验收对照

[验收基线](acceptance.md) 固定既有用例的对照来源及新增操作的预期结果。保留原来的无人操作冒烟，另起或重置仿真环境执行 Ops 场景，按各自口径报告。
